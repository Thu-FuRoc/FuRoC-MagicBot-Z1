# AGENTS.md

This file provides guidance to Codex and other coding agents when working with code in this repository.

## Project Overview

RL locomotion training pipeline for the MagicBot Z1 12DOF bipedal robot. Three parallel training strategies share a unified orchestrator and RTX server workflow:

| Strategy | Directory Prefix | Status |
|----------|------------------|--------|
| A. Legged Gym | `A_legged_gym` | Done (`p1`-`p4`) |
| B. Custom Curriculum | `B_custom_curriculum` | In progress |
| C. AMP | `C_amp` | Planned |

## Common Commands

### Training

Training runs on the RTX server `phh@192.168.120.155` with conda env `isaaclab`.

```bash
# Orchestrated pipeline via SLURM
sbatch scripts/z1_orchestrator.slurm
sbatch scripts/z1_orchestrator_legged_gym.slurm

# Direct orchestrator
python scripts/automation/phase_orchestrator.py \
    --plan config/pipeline/z1_custom_5phase_plan.yaml \
    --num-gpus 4 \
    --poll-interval 120
```

### Video Recording

The active recorder lives one level above the repo root:

```bash
python ..\rtx_record_video.py --phase p3_coarse --yes
```

Outputs land in `videos/{strategy}/{phase}/{YYYYMMDD_HHMM_modelXXXX}/` and include:
- labeled IsaacLab video
- `parameters/record_meta.json`
- `parameters/sweep.json`
- config snapshots such as `deploy.yaml` and `velocity_env_cfg.py`

### Local Playback

```bash
python scripts/local_play_gui.py
```

The GUI auto-discovers presets from `models/A_legged_gym/` and `models/B_custom_curriculum/`. JIT export runs automatically for raw checkpoints that have not yet been converted.

### Analysis

```bash
python scripts/analyze_sim_log.py <csv_path>
python scripts/plot_learning_curves.py --log_root <path> --output_dir <path>
python scripts/label_video.py <video> --run <phase> --model <model_stem>
```

## Architecture

### Orchestrator

Main entrypoint: `magiclab_rl_lab/scripts/automation/phase_orchestrator.py`

The orchestrator is plan-driven and strategy-agnostic. The selected YAML plan in `config/pipeline/` determines which strategy runs.

Execution model:
1. Iterate phases, then sub-phases (`coarse` / `fine`).
2. Generate runtime config through a three-layer merge: `defaults -> phase -> sub_phase`.
3. Swap the active env config file `velocity_env_cfg.py`.
4. Launch distributed PPO with `torchrun`.
5. Monitor for overfitting and instability signals.
6. Apply rollback logic when reward drops below threshold.
7. Run post-phase export, video, labeling, and plotting steps.

State persists in `orchestrator_state.json`. Resume via `--resume`.

### Config Generation

Config generator: `magiclab_rl_lab/scripts/automation/config_generator.py`

Plans use a three-layer merge model:

```yaml
defaults:
  training:
    num_envs_per_gpu: 1024
phases:
  p1:
    training:
      max_iterations: 3000
    sub_phases:
      coarse: {}
      fine:
        training:
          max_iterations: 2000
```

PPO overrides are passed through `--agent_cfg` with a temporary file. Do not edit the base agent config in place.

### Tracking System

Tracking files:
- `docs/tracking/bestmodel_phase.json`
- `docs/tracking/bestmodel_custom.json`
- `docs/tracking/bestmodel_legged.json`

Canonical field name: `best_checkpoint_path`

Status values: `PLANNED`, `RUNNING`, `COMPLETE`, `STOPPED`, `ARCHIVED`

### Local Play GUI Presets

`scripts/local_play_gui.py` contains `PRESET_RUNTIME_BINDINGS`, mapping preset names to runtime fields such as phase, terrain, and flat-ground mode.

Current preset groups:
- `p1_coarse` / `p1_fine` / `p2_coarse` / `p2_fine` / `p3_coarse` / `p3_fine` for `B_custom_curriculum`
- `p1` / `p2` / `p3` / `p4` for `A_legged_gym`

### Video Config

Manifest files:
- `config/video/video_record_targets_current.json`
- `config/video/video_record_targets_a_legged_gym.json`

The older `record_best_videos_remote.py` flow is obsolete. Use `..\rtx_record_video.py`.

## Project Conventions

- Training logs should be written in Chinese.
- Bug-fix records should include both root cause and fix, kept concise.
- Prefer copy-paste-ready SSH commands when giving remote-operation instructions.
- Use `best_checkpoint_path`, not `best_model_path`.
- Keep property naming and tracking fields consistent with the existing JSON files and scripts.
